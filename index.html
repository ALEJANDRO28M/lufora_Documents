LUFORA S.A.S. · Backend

Manual del backend LUFORA

Qué hace cada archivo, por qué existe y qué se rompería si no estuviera. Escrito para que puedas construir el siguiente módulo tú mismo, con el mismo criterio con el que se construyó este.

Cómo pienso el problema antes de escribir código

Ningún archivo del proyecto se decidió mientras se escribía. Todos salen de estas cinco preguntas, en este orden.

  1. ¿Qué vende el negocio, en una frase?

    De la frase salen los sustantivos, y los sustantivos son casi siempre las tablas.

    "LUFORA vende productos tecnológicos de varias marcas, organizados por categoría, con stock y garantía." → producto, marca, categoría, stock, garantía.
  2. ¿Qué preguntas le van a hacer a la API?

    Diseñar desde las preguntas reales evita construir lo que nadie pide. Cada pregunta se convierte en un endpoint o en un filtro.

    "Dame los portátiles de menos de 3 millones" → filtros de categoría y precio. "Abre este producto desde un enlace" → obliga a tener slug, no solo id.
  3. ¿Qué NO va a existir todavía?

    Decidir lo que se deja fuera es la mitad del diseño. Lo que no está no se mantiene, no se prueba y no se rompe.

    En la Fase 1 no hay usuarios, ni carrito, ni pagos, ni historial de inventario. El catálogo funciona sin nada de eso.
  4. ¿Qué se puede construir primero?

    Lo que no depende de nada más. Esa es toda la lógica del orden de las fases.

    El catálogo no necesita usuarios. Los pedidos sí — necesitan saber quién compra. Por eso el catálogo va primero y pedidos va cuarto.
  5. ¿Qué va a cambiar seguro?

    Lo que va a cambiar se aísla; lo que es estable se escribe directo. Este es el criterio que decide dónde poner una interfaz y dónde no.

    El proveedor de pagos puede cambiar → interfaz. Guardar un producto en MySQL no va a cambiar → código directo.

El orden de construcción

Cada paso solo depende de los anteriores. Si lo inviertes, te quedas escribiendo código contra cosas que todavía no existen.

01pom.xmlQué librerías existen. Sin esto, ningún import compila.
02application.ymlCómo se conecta a la base y en qué puerto escucha.
03V1__esquema.sqlLas tablas. El esquema manda: la entidad se adapta a la tabla, no al revés.
04domain/Las entidades, que reflejan esas tablas.
05repository/Cómo se consultan. Necesita que la entidad exista.
06dto/Qué entra y qué sale por la API. Se decide antes del service.
07mapper/El puente entre entidad y DTO. Necesita ambos.
08service/Las reglas del negocio. Usa repository y mapper.
09web/La puerta HTTP. Es lo último porque solo delega.
10peticiones.httpProbar de verdad lo que acabas de construir.
Por qué la base de datos va antes que la entidad. Podrías dejar que Hibernate genere las tablas desde tus clases. No lo hacemos: en este proyecto Hibernate está en modo validate, que solo verifica y nunca modifica. La razón es que el esquema es lo más difícil de corregir después — cuando ya hay datos reales dentro. Escribirlo a mano te obliga a pensarlo, y cada cambio queda versionado en git como un archivo V2, V3, V4.

Arranque y configuración

Los cinco archivos que hacen que la aplicación exista y se levante.

pom.xmlConfiguración

La lista de librerías del proyecto y cómo se empaqueta. Maven lee este archivo, descarga cada dependencia y las pone a disposición del compilador.

Lo clave

Hereda de spring-boot-starter-parent. Eso significa que no escribes versiones para casi nada: Spring Boot ya decidió qué versión de cada librería funciona bien con las demás. Es la razón por la que un proyecto Spring "simplemente funciona" mientras que armar las versiones a mano es una pesadilla.

Sin él: no existe proyecto. Maven no sabría qué compilar ni con qué.
LuforaBackendApplication.javaConfiguración

El punto de arranque. Tiene el main que levanta todo.

Lo clave

@SpringBootApplication hace tres cosas a la vez: activa la configuración automática, marca esta clase como fuente de configuración, y —lo más importante— escanea todos los paquetes por debajo de este. Por eso la clase vive en com.lufora.tienda y no en una subcarpeta: si estuviera más abajo, Spring no encontraría tus controllers.

@EnableJpaAuditing es lo que hace que las fechas de creación se llenen solas.

application.ymlConfiguración

Datos de conexión, puerto, comportamiento de Hibernate y Flyway.

Lo clave

Las credenciales se escriben como ${DB_USER:lufora}: usa la variable de entorno si existe, y si no, el valor por defecto. Así el mismo archivo sirve en tu máquina y en producción sin tener contraseñas escritas dentro.

open-in-view: false evita un problema clásico: sin eso, Spring deja la conexión a la base abierta mientras se genera el JSON, y las consultas se disparan sin que te des cuenta.

config/WebConfig.javaConfiguración

Permite que tu frontend, que corre en otro puerto, pueda llamar a la API.

Lo clave

El navegador bloquea por seguridad las llamadas entre orígenes distintos. Esto es CORS. Aquí se declara qué orígenes tienen permiso, leídos desde application.yml para no dejarlos escritos en el código.

Sin él: tu frontend recibiría un error de CORS en el navegador y no podría consumir nada, aunque la API funcione perfecto desde Postman.
config/OpenApiConfig.javaConfiguración

Le pone título y descripción a la documentación automática en /docs.

Lo clave

Springdoc lee tus controllers y genera Swagger solo. Esta clase solo personaliza la portada. El valor real es que quien construya el frontend consulta la API sin preguntarte nada.

La base de datos

Flyway ejecuta estos archivos en orden la primera vez que arranca la app, y lleva registro de cuáles ya aplicó en una tabla propia.

V1__esquema_catalogo.sqlBase de datos

Crea las cuatro tablas: marcas, categorias, productos y producto_imagenes.

Decisiones que están dentro

Claves foráneas reales. La base rechaza un producto con una marca inexistente. La validación en Java puede fallar; la de la base no.

Restricciones únicas en sku y slug. Aunque dos peticiones lleguen en el mismo milisegundo, no habrá duplicados.

DECIMAL(12,2) para el dinero. Nunca FLOAT: con decimales binarios, sumar centavos da errores de redondeo, y en facturación eso es un problema legal.

Índices en las columnas por las que se filtra. Sin ellos, buscar por categoría recorre la tabla entera.

ON DELETE CASCADE en imágenes: borrar un producto borra sus fotos, sin dejar basura.

V2__datos_demo.sqlBase de datos

Marcas, categorías y tres productos de ejemplo, para que la API responda algo desde el primer arranque.

Antes de producción: bórralo. Son datos de prueba, no tu catálogo.
Cómo nombrar las siguientesBase de datos

El formato es obligatorio: V + número + __ (dos guiones bajos) + descripción.

V3__inventario.sql
V4__usuarios_y_roles.sql
V5__pedidos.sql
La regla que no se rompe

Un archivo ya aplicado nunca se edita. Flyway guarda una huella de cada uno; si la cambias, se niega a arrancar. ¿Te equivocaste en V3? Corriges con un V4 nuevo.

Piezas compartidas

Viven en common/ porque los tres módulos que faltan las van a usar igual que catálogo.

common/domain/BaseEntity.javaCompartido

Contiene el id y las fechas de creación y actualización. Todas las entidades la heredan.

Lo clave

Es @MappedSuperclass: no genera una tabla propia; sus columnas se copian a cada tabla hija. Combinado con @CreatedDate, las fechas se llenan solas — nunca las asignas a mano.

Sin ella: repetirías cuatro campos idénticos en cada entidad, y tarde o temprano se te olvidaría poner la fecha en alguna.
common/dto/PageResponse.javaCompartido

El formato de respuesta cuando devuelves una lista paginada.

Por qué no devolver la clase Page de Spring

Spring tiene su propia clase Page, pero su JSON cambia entre versiones del framework. Si la expusieras, una actualización de Spring rompería tu frontend sin que tocaras una línea. Con esta clase, tú controlas el contrato.

exception/RecursoNoEncontradoException.javaCompartido

Se lanza cuando piden algo que no existe. El manejador global la traduce a un 404.

exception/ReglaNegocioException.javaCompartido

Se lanza cuando la petición es válida pero rompe una regla — un SKU repetido, un stock que quedaría negativo. Se traduce a un 409.

Por qué dos excepciones y no una

Porque significan cosas distintas para quien consume la API. "No existe" y "existe pero no puedes" merecen códigos HTTP diferentes, y el frontend reacciona distinto a cada uno.

exception/GlobalExceptionHandler.javaCompartido

Atrapa las excepciones de toda la aplicación y las convierte en respuestas con formato uniforme.

Lo clave

Es @RestControllerAdvice: Spring lo aplica a todos los controllers sin que ninguno lo sepa. Cada tipo de error tiene su método. El de validación es especialmente útil: devuelve campo por campo qué estuvo mal, en vez de un mensaje genérico.

Sin él: cada controller tendría bloques try/catch repetidos, y los errores saldrían con formatos distintos según dónde ocurrieran. Peor: Spring devolvería trazas internas al cliente.
exception/ErrorResponse.javaCompartido

La forma exacta de un error: momento, código, mensaje, ruta y, si aplica, los campos inválidos.

Es un record: una clase inmutable en una línea, sin getters escritos a mano. Java 21 los hace ideales para DTOs.

util/SlugUtil.javaCompartido

Convierte "Portátil Lenovo 15\"" en portatil-lenovo-15.

Para qué sirve realmente

Para que las URLs sean legibles: /productos/slug/portatil-lenovo-15 en vez de /productos/847. Google indexa mejor la primera y el cliente entiende dónde está parado.

Es la única clase con test unitario, por una razón: es lógica pura, sin base de datos ni framework. Ese tipo de código es el más fácil y el más rentable de probar.

El dominio

Las clases que se corresponden con las tablas. Cada campo es una columna; cada relación, una clave foránea.

domain/Producto.javaDominio

La entidad central. Todo lo demás gira alrededor de ella.

Detalles que importan

Relaciones en LAZY. Al cargar un producto no se trae automáticamente su marca ni su categoría; se traen solo si alguien las pide. Con EAGER, listar 50 productos dispararía decenas de consultas extra.

@Enumerated(EnumType.STRING) guarda "NUEVO" como texto, no como número. Si guardaras el número y mañana reordenas el enum, todos los datos viejos cambiarían de significado en silencio.

Métodos con reglas dentro: hayStock() y stockEnMinimo(). La entidad no es solo un contenedor de datos; sabe responder preguntas sobre sí misma. Eso evita repetir la misma comparación en cinco servicios distintos.

domain/Marca.java · Categoria.javaDominio

Tablas de apoyo del catálogo.

Lo interesante de Categoria

Tiene una relación consigo misma (categoriaPadre). Eso permite subcategorías —"Celulares" → "Gama alta"— sin crear tablas nuevas. Cuando el padre es nulo, es una categoría raíz, y de ahí sale el menú del sitio.

domain/ProductoImagen.javaDominio

Las fotos de un producto, con orden y marca de cuál es la principal.

Lo clave

La relación desde Producto lleva cascade = ALL y orphanRemoval = true: guardar el producto guarda sus imágenes, y quitar una de la lista la borra de la base. La lista se mantiene ordenada con @OrderBy.

domain/EstadoProducto.javaDominio

Un enum: NUEVO, REACONDICIONADO, USADO.

Usar un enum en vez de texto libre hace imposible escribir "nuevoo". El compilador lo impide antes de que llegue a la base.

Acceso a datos

Cómo se consulta la base sin escribir SQL a mano.

repository/ProductoRepository.javaDatos

Una interfaz sin implementación. Spring genera la clase real al arrancar.

Cómo funciona por dentro

Spring Data lee el nombre del método y construye la consulta:

findByDestacadoTrueAndActivoTrue()
→ WHERE destacado = true AND activo = true

findBySlug(String slug)
→ WHERE slug = ?

Cuando el nombre se volvería impronunciable, se escribe la consulta con @Query — como en findConStockBajo(), que compara dos columnas entre sí.

Hereda también de JpaSpecificationExecutor, y eso es lo que habilita la búsqueda con filtros combinables.

spec/ProductoSpecs.javaDatos

Cada filtro de búsqueda como una pieza suelta que se puede combinar con las demás.

El problema que resuelve

La búsqueda tiene siete filtros opcionales. Escribir un método por combinación serían más de cien métodos. Aquí cada filtro es independiente y devuelve null cuando no aplica; el service solo suma los que llegaron con valor, y Spring arma una única consulta SQL con lo que quedó.

Sin esto: terminarías construyendo SQL pegando texto, que es lento de mantener y abre la puerta a inyección SQL.

DTOs y mapper

DTO significa objeto de transferencia: lo que viaja entre tu API y quien la consume. Nunca viaja la entidad.

dto/ProductoRequest.javaEntrada

Lo que el cliente envía para crear o actualizar un producto.

Lo clave

Las anotaciones (@NotBlank, @DecimalMin, @Min) validan antes de que el código del service se ejecute. Si algo falla, el manejador global responde 400 con la lista de campos malos.

Fíjate que recibe marcaId, no un objeto Marca completo. El cliente manda identificadores; el service resuelve los objetos.

dto/ProductoResponse.javaSalida

El detalle completo que devuelve la API.

Aquí está la razón de ser de todo esto

La entidad Producto tiene un campo costo — lo que te costó a ti. Este DTO no lo incluye. Si devolvieras la entidad directamente, tu margen de ganancia estaría publicado en internet para cualquiera que abra las herramientas de desarrollador.

También agrega disponible, un campo calculado que no existe en la base: se deduce del stock.

dto/ProductoResumenResponse.javaSalida

Versión liviana para los listados.

Por qué existen dos DTOs de salida

Una grilla de 12 productos no necesita la descripción completa ni todas las imágenes de cada uno. Mandar solo lo que la pantalla muestra hace la respuesta varias veces más pequeña — y en móvil con datos, eso se nota.

dto/ProductoFiltro.javaEntrada

Agrupa los siete parámetros de búsqueda en un solo objeto.

Sin él, el service recibiría siete argumentos sueltos y agregar un filtro nuevo obligaría a cambiar la firma del método en varios sitios.

mapper/CatalogoMapper.javaAplicación

Convierte entidades en DTOs. Un solo lugar, escrito a mano.

Por qué a mano y no con una librería

Existe MapStruct, que genera esto automáticamente. Se hizo manual a propósito: es explícito, se lee sin conocer otra herramienta, y no agrega dependencias. Cuando el proyecto tenga treinta entidades, ahí sí vale la pena cambiarlo.

Nótese que aquí es donde se decide qué campos se ocultan y cuáles se calculan. Es el guardián del contrato de tu API.

Los servicios

Donde vive el negocio. Si algún día migras a otro framework web, esta es la capa que sobrevive.

service/ProductoService.javaAplicación

Crear, actualizar, buscar, ajustar stock y desactivar productos.

Las transacciones

La clase lleva @Transactional(readOnly = true) y los métodos que escriben lo sobrescriben con @Transactional. Una transacción es todo o nada: si algo falla a mitad, se deshace completo. El modo solo-lectura además le permite a la base optimizar las consultas.

Un detalle que se ve pequeño y no lo es

En los métodos de actualización no se llama a save(). Dentro de una transacción, JPA detecta los cambios sobre un objeto cargado y los guarda al terminar. Se llama dirty checking. Sorprende la primera vez que se ve.

Slugs únicos

Si ya existe portatil-lenovo, el siguiente será portatil-lenovo-2. Sin eso, la restricción única de la base rechazaría el segundo producto con un error feo.

Validaciones que la base no puede hacer

Que un ajuste no deje el stock negativo, o que el SKU no esté tomado por otro producto. Son decisiones de negocio, y por eso viven aquí y no en el controller.

service/MarcaService.java · CategoriaService.javaAplicación

El mismo patrón, más simples.

La regla que protege el menú

CategoriaService impide que una categoría sea su propia madre. Sin esa validación, armar el menú del sitio entraría en un ciclo infinito.

Borrado lógico

Los tres servicios "borran" poniendo activo = false. Un producto borrado de verdad rompería el historial de pedidos que lo referencian — y ese historial es tu contabilidad.

Los controllers

La puerta HTTP. Son los archivos más cortos del proyecto, y así debe ser.

web/ProductoController.javaWeb

Nueve endpoints. Ninguno decide nada: reciben, delegan y responden.

Las URLs llevan versión

/api/v1/productos. Cuando necesites cambiar el formato de respuesta sin romper a quien ya consume la API, publicas /v2 y ambas conviven. Agregarlo después es carísimo.

Dos formas de pedir un producto

Por id para uso interno, y por slug para las URLs públicas del sitio. Misma información, distinto camino.

Los códigos HTTP correctos

Crear devuelve 201 con la cabecera Location apuntando al recurso nuevo. Desactivar devuelve 204, sin cuerpo. Son convenciones que cualquier cliente REST espera.

La paginación viene gratis

@PageableDefault hace que ?page=0&size=12&sort=precio,asc funcione sin escribir nada. Sin paginación, el día que tengas 5.000 productos una sola petición tumbaría la aplicación.

web/MarcaController.java · CategoriaController.javaWeb

CRUD estándar sobre marcas y categorías, con el mismo patrón.

?soloActivas=true y ?soloRaices=true permiten que el mismo endpoint sirva al panel de administración y al menú público.

peticiones.httpWeb

Todas las llamadas listas para ejecutar desde IntelliJ o desde VS Code con la extensión REST Client.

Vive dentro del repositorio a propósito: cuando alguien más entre al proyecto, no tiene que adivinar cómo se usa la API.

Receta: construir el módulo de inventario

Tu Fase 2, paso a paso. Sigue este orden y el proyecto compila después de cada paso. Es el mismo camino que se usó para catálogo.

  1. Define qué guardas, en papel

    Un movimiento tiene: producto, tipo (entrada, salida o ajuste), cantidad, motivo, fecha y quién lo hizo. Escríbelo antes de tocar el teclado.

  2. Escribe la migración

    La tabla movimientos_inventario con su clave foránea al producto y un índice por producto y fecha.

    resources/db/migration/V3__inventario.sql
  3. Crea el módulo

    Una carpeta hermana de catalogo, con las mismas subcarpetas.

    tienda/inventario/{domain, repository, dto, service, web}
  4. El enum y la entidad

    TipoMovimiento y MovimientoInventario extends BaseEntity, con la relación al producto en LAZY.

    inventario/domain/
  5. El repositorio

    Buscar movimientos por producto ordenados por fecha, y por rango de fechas para los reportes.

    inventario/repository/
  6. Los DTOs

    Uno de entrada para registrar el movimiento, uno de salida para mostrarlo con el nombre del producto ya resuelto.

    inventario/dto/
  7. El servicio — aquí está lo importante

    Registrar el movimiento y actualizar el stock del producto deben ocurrir dentro de la misma transacción. Si se guarda el movimiento pero falla el stock, tu inventario queda mintiendo. Un solo método con @Transactional resuelve esto.

    inventario/service/InventarioService
  8. El controller

    Registrar un movimiento y consultar el historial de un producto.

    inventario/web/InventarioController
  9. Jubila el ajuste viejo

    El PATCH /productos/{id}/stock actual deja de usarse: ahora todo movimiento pasa por inventario y queda registrado.

  10. Pruébalo

    Agrega las llamadas nuevas a peticiones.http y verifica que el stock del producto cambie al registrar un movimiento.

Cuando dudes dónde va un archivo, hazte la pregunta de la capa: ¿define una URL? Va en web/. ¿Toma una decisión o valida una regla? Va en service/. ¿Habla con la base? Va en repository/. ¿Es una tabla? Va en domain/. ¿Lo van a usar otros módulos? Va en common/.

Producción y GitHub

Los archivos que no son código de la aplicación pero deciden si el proyecto es serio o no.

DockerfileProducción

Construcción en dos etapas: la primera compila con Maven, la segunda copia solo el .jar a una imagen con únicamente el Java necesario para ejecutar.

Por qué dos etapas

La imagen final no lleva Maven, ni el compilador, ni tu código fuente. Pesa una fracción y expone mucho menos. Además corre con un usuario sin privilegios, no como root.

.github/workflows/ci.ymlProducción

En cada push, GitHub compila el proyecto y corre los tests contra un MySQL real, no una base falsa en memoria.

Por qué MySQL de verdad

Porque una base en memoria acepta cosas que MySQL rechaza. Si pruebas contra algo distinto a producción, los tests pasan y el despliegue falla.

.gitignore · .env.exampleProducción

El primero bloquea que subas credenciales, compilados o archivos del IDE. El segundo documenta qué variables hay que configurar, sin contener ningún valor real.

Esto no es opcional: una contraseña subida a git queda en el historial para siempre, aunque borres el archivo después.
docker-compose.ymlDesarrollo

Levanta MySQL con un comando, sin instalar nada en tu equipo. Los datos sobreviven a reinicios gracias a un volumen.

docker compose down -v borra ese volumen: úsalo cuando quieras empezar de cero.

Subirlo a GitHub

Crea el repositorio vacío en GitHub —sin README, sin licencia— y desde la carpeta del proyecto:

git init -b main
git add .
git commit -m "Fase 1: modulo de catalogo"
git remote add origin https://github.com/TU_USUARIO/lufora-backend.git
git push -u origin main

Antes de subir, revisa que .env no aparezca en git status. Y elige repositorio privado: este es el código de tu empresa.
